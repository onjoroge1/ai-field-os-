# PR29 — Backup, restore and disaster recovery

## Recovery objectives and ownership

Pilot targets: database RPO <= 60 minutes; service RTO <= 4 hours from incident declaration, subject to a successful production-sized drill. These are targets, not measured guarantees. The recovery lead owns restore/cutover, the security lead owns keys/access, and the tenant owner validates representative workflows. Record incident times, bundle time, restored business checkpoint, validation results and approval to reopen writes. CI reports restore duration for a disposable fixture; it does not prove production RPO/RTO, offsite availability or a live failover.

## Backup operation

Configure `FIELD_OS_BACKUP_DEST` as an absolute directory on protected, independently administered offsite storage, outside the site directory, and `FIELD_OS_BACKUP_KEY_B64` as a secret containing 32 random bytes encoded in base64. Keep key versions in a separate secret manager and preserve each key until every dependent backup expires. Do not store the key beside backups, commit it, put it in a shell argument, or include it in logs. Mount destination permissions as 0700; reserve capacity and monitor both the storage mount and scheduler. This PR does not provision remote storage or a key vault.

The hourly long scheduler creates fresh native database and compressed public/private file archives plus site configuration in a private temporary directory. It encrypts all four components and a manifest using streaming AES-256-GCM with unique nonces, authenticated component labels and SHA-256 content validation. A complete encrypted directory is published by atomic rename; failures publish no success bundle. Temporary plaintext is removed after normal success/failure. Use encrypted scratch volumes and a restricted host because secure erasure after crashes is a storage concern. A missing key fails closed. Site-wide backups include every tenant and are accessible only to infrastructure administrators. They are never tenant downloads.

Use an offsite filesystem with durable rename semantics or copy completed bundles to versioned object storage; copying `.pending` directories is prohibited. Validate object checksums and replication completion before treating a backup as offsite. Retain hourly backups for 48 hours, daily backups for 30 days, and monthly backups for 12 months, with immutability enabled by the storage administrator. This PR does not delete older backups automatically. Capacity and retention must be configured before enabling scheduling. Monitor `Field OS Recovery Run` and `erpnext.field_os.recovery.service.health` from the infrastructure monitor; page for a failed run or no success within 75 minutes.

Database dumps use the native database snapshot. File archives are sequential, so database/file consistency during concurrent file deletion or modification is not guaranteed. Use a storage snapshot or a deployment-level write/worker pause for a consistent recovery checkpoint before migrations and production drills. Record that checkpoint in the incident log. Hourly unattended backups improve recovery coverage but cannot substitute for validating referenced files after restore.

## Restore to a clean environment

1. Declare the incident. Pause ingress and external-side-effect workers; preserve evidence and the failed deployment. Select a known-good complete bundle and its key version. Record the bundle timestamp and expected data loss. Provision an isolated host with the same Frappe/ERPNext revisions, database engine and encryption dependencies. Block outbound email, SMS, payment and model network access and leave scheduler/workers stopped.
2. Inject the matching backup key via the secret manager. From the app runtime run `python -m erpnext.field_os.recovery.bundle /protected/bundle /protected/NEW-stage`. The output directory must not exist. Decryption and hashes must all pass; any failure removes staged plaintext. No database is modified by this command.
3. Create a NEW Frappe site and database. Keep its new database credentials and recovery host configuration. Transfer the application `encryption_key` from the verified `site_config.json` into the recovery site's restricted configuration so saved provider passwords decrypt. Preserve any separately used native backup key in the secret vault. Never overwrite the recovery database credentials with the source config or print either config.
4. Restore `database.sql.gz` with `bench --site NEW-SITE restore`, supplying `--with-public-files` and `--with-private-files` paths to the staged archives. Use the deployment's secure credential injection mechanism. Migrate using the pinned compatible app versions. Set the site's maintenance mode, scheduler pause, email mute and provider egress blocks before reconnecting services. Do not repoint DNS yet.
5. Validate company and customer counts, equipment/jobs/estimates/invoices, usage ledger, private attachments, application credential decryption, login and cross-tenant permissions. Reconcile any Running/Uncertain outbound jobs against provider records before replay; a backup can predate a successful external send or payment webhook. Refresh Stripe subscriptions and invoices from current provider state. Review changes between backup and incident cutoff rather than blindly replaying old notifications.
6. Obtain the incident commander's cutover decision after validation. Switch traffic, monitor errors/latency and selectively re-enable workers/integrations. Keep the previous environment fenced for rollback. Record achieved RPO/RTO and residual gaps, then securely remove staged plaintext and rotate incident-exposed credentials.

## Verification and rehearsal

Run the encrypted bundle tests on every change. CI restores the encrypted database and both file archives into a newly created `fieldos-restore.test` site, copies only the application encryption key, migrates and verifies business counts, a private file hash, a saved encrypted credential and tenant isolation. It refuses an existing target and only seeds disposable `.test` sites with `allow_tests`. The report is `recovery-drill.json`; no backup or decryption key is uploaded as an artifact.

Run a production-sized isolated restore monthly and before destructive schema changes. Include missing/wrong key, corrupted archive, unavailable storage, missing attachment, interrupted workers, stale payment events and failed cutover scenarios. A failed integrity check stops restore. If migration fails, keep the recovery site isolated and restore a new copy with the matching old revision; do not edit the sole backup. If the new environment fails after cutover, fence its writes, reconcile transactions and approve return to the preserved environment. Billing checkout/security review, external monitoring delivery and live recovery infrastructure remain deployment gates outside this fixture drill.
